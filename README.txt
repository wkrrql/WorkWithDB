Часть 1. ПОЛНЫЙ ПЕРЕЧЕНЬ СИСТЕМНЫХ И КОРПОРАТИВНЫХ ТРЕБОВАНИЙ (Условие задачи)

Ниже приведен жесткий регламент проектирования «идеально-архитектурного» решения. 
Каждый пункт обязателен к выполнению и проверяется автоматизированными тестами, 
а также в процессе Code Review.

1.  РАЗРАБОТКА ENTITY-КЛАССОВ (СУЩНОСТЕЙ)
    1.1. На основе нормализованной схемы базы данных должны быть созданы 
         соответствующие POJO классы (Plain Old Java Objects): Film, Actor, Director.
    1.2. Сущности должны являться классическими носителями данных (Data Holders). 
         В них строго запрещено размещать методы бизнес-логики: любые вычисления, 
         сетевые запросы, операции валидации или методы прямого обращения к 
         базе данных.
    1.3. Каждый Entity-класс обязан содержать уникальный идентификатор (поле id) 
         соответствующего типа (int или long), соотносящийся с первичным ключом (PK) 
         в СУБД.
    1.4. Поля сущностей должны быть инкапсулированы (private) и снабжены 
         стандартными методами доступа (getters). Сеттеры (setters) не рекомендуются 
         для обеспечения иммутабельности объектов после их сборки.

2.  ПАТТЕРН ПРОЕКТИРОВАНИЯ BUILDER (СТРОИТЕЛЬ)
    2.1. Создание любых экземпляров Entity-классов из внешнего кода через прямые 
         конструкторы (new Film(...)) запрещено.
    2.2. Внутри каждого Entity-класса должен быть реализован статический вложенный 
         класс Builder, предоставляющий fluent-интерфейс для пошаговой инициализации 
         полей объекта.
    2.3. Метод build() должен возвращать полностью сконструированный и готовый 
         к работе объект сущности.

3.  ПЕРЕОПРЕДЕЛЕНИЕ БАЗОВЫХ МЕТОДОВ КЛАССА OBJECT
    3.1. Для всех Entity-классов должны быть явно переопределены методы:
         equals(Object o), hashCode(), toString().
    3.2. КРИТИЧЕСКОЕ ТРЕБОВАНИЕ: При реализации equals() и hashCode() ЗАПРЕЩЕНО 
         использование вспомогательных утилитарных классов JDK, таких как 
         java.util.Objects (методы Objects.equals(), Objects.hash()). Расчет 
         хэш-кода и побитовое/ссылочное сравнение полей должны выполняться вручную 
         с использованием классических алгоритмов (например, алгоритм Джошуа Блоха 
         с множителем 31 и побитовым сдвигом >>>).

4.  ОРГАНИЗАЦИЯ СЛОЯ ДОСТУПА К ДАННЫМ (DAO & REPOSITORY С СИСТЕМОЙ СПЕЦИФИКАЦИЙ)
    4.1. Организация соединения с базой данных (MySQL) должна быть изолирована 
         в отдельном инфраструктурном классе (ConnectionFactory или ConnectionPool), 
         единственный метод которого возвращает объект java.sql.Connection. 
         Прямое хардкодирование DriverManager в коде DAO запрещено.
    4.2. База данных должна находиться как минимум в 3-й нормальной форме (3NF). 
         Связи «многие-ко-многим» (Фильмы-Актеры, Фильмы-Режиссеры) должны быть 
         вынесены в отдельные таблицы связей (film_actors, film_directors) 
         с каскадным удалением (ON DELETE CASCADE) на уровне внешних ключей (FK).
    4.3. Работа с базой данных должна быть разделена на два изолированных класса:
         - Класс извлечения (Чтения) информации.
         - Класс модификации (Записи/Обновления/Удаления) информации.
    4.4. Все SQL-запросы внутри DAO обязаны использовать скомпилированные запросы 
         (java.sql.PreparedStatement). Использование обычных Statement и 
         конкатенации строк в SQL-запросах КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО во избежание 
         уязвимостей SQL Injection.
    4.5. Для фильтрации и поиска данных должен быть применен паттерн Specification 
         (Спецификация). Вместо создания множества жестко прописанных методов 
         поиска в DAO, класс чтения должен содержать универсальный метод 
         query(Specification specification), который динамически подставляет 
         условия WHERE, JOIN, GROUP BY и HAVING, генерируемые объектами спецификаций.

5.  БИЗНЕС-ЛОГИКА И ВАЛИДАЦИЯ (SERVICE & VALIDATOR LAYERS)
    5.1. Вся прикладная логика приложения должна быть сосредоточена в классах 
         бизнес-сервисов (например, FilmService). Сервисы координируют работу DAO, 
         обрабатывают полученные объекты и управляют транзакциями (при наличии).
    5.2. Перед передачей данных в слой модификации (DAO) или при обработке 
         входных параметров, данные должны проходить через слой специализированных 
         валидаторов (например, FilmValidator). Валидаторы проверяют бизнес-правила 
         (например: имя фильма не пустое, дата релиза не находится в далеком будущем, 
         длина полей соответствует ограничениям БД).

6.  ИНФРАСТРУКТУРНЫЕ ТРЕБОВАНИЯ: ЛОГИРОВАНИЕ И ИСКЛЮЧЕНИЯ
    6.1. Использование System.out.println() и System.err.println() для вывода 
         информации о работе программы в консоль КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО.
    6.2. В проект должна быть подключена система логирования через фасад SLF4J 
         и движок Log4J2 (настройка через log4j2.xml).
    6.3. Логирование должно вестись на разных уровнях (DEBUG, INFO, WARN, ERROR) 
         и одновременно дублироваться как в консоль разработчика, так и в циклический 
         файл логов (logs/cinema-app.log).
    6.4. В приложении запрещено пробрасывать низкоуровневые исключения вроде 
         java.sql.SQLException на верхние слои (в Service или Main). Все SQLException 
         должны перехватываться в DAO, логироваться и оборачиваться в кастомные 
         архитектурные исключения: DaoException и ServiceException.

7.  ТРЕБОВАНИЯ К UNIT-ТЕСТИРОВАНИЮ (КОРПОРАТИВНЫЙ СТАНДАРТ)
    7.1. Проект должен быть покрыт модульными тестами с использованием JUnit 5.
    7.2. Бизнес-логика (Service) должна тестироваться изолированно от базы данных 
         с применением фреймворка Mockito для создания «заглушек» (Mocks) слоя DAO.
    7.3. ЖЕСТКОЕ ОГРАНИЧЕНИЕ ДЛЯ КОДА ТЕСТОВ: При написании тестовых методов 
         категорически запрещено использовать:
         - Любые неаннотированные методы (каждый метод должен быть @Test, 
           @ParameterizedTest и т.д.).
         - Логирование и вывод в консоль.
         - Операторы ветвления и циклы: if, for, while, do-while, switch.
    7.4. Для тестирования множества сценариев без циклов необходимо использовать 
         параметризованные тесты (@ParameterizedTest, @CsvSource, @MethodSource). 
         Для групповых проверок полей объектов использовать assertAll().

Часть 2. ТЕХНИЧЕСКОЕ И АРХИТЕКТУРНОЕ ОБОСНОВАНИЕ ВЫБРАННЫХ РЕШЕНИЙ
Ниже детально разобрано, почему выбрано каждое архитектурное решение.

1.  ОБОСНОВАНИЕ: Почему Entity-классы лишены бизнес-логики (Anemic Domain Model)?
    - Разделение ответственности (Separation of Concerns): Задача Entity — просто 
      представлять слепок данных из таблицы БД в оперативной памяти Java. Если мы 
      поместим туда логику расчетов, класс станет «божественным объектом» (God Object), 
      который тяжело изменять, читать и тестировать. Изоляция данных в Entity 
      делает их легковесными и абсолютно независимыми от контекста использования.

2.  ОБОСНОВАНИЕ: Зачем нужен паттерн Builder?
    - Защита от создания некорректных объектов: У фильма или актера может быть 
      много полей (id, name, date, country, etc.). Использование классических 
      конструкторов приводит к двум проблемам:
      1) Телескопический конструктор: Плодится куча конструкторов с разным числом 
         параметров, в которых легко запутаться и перепутать местами две строки (String).
      2) Использование сеттеров (JavaBeans-стиль) позволяет создать пустой объект 
         и забыть засетить критически важное поле, оставив объект в "полу-сломанном" 
         невалидном состоянии.
    - Иммутабельность (Неизменяемость): Объект собирается через Builder, поля сущности 
      объявляются как 'private final', у них отсутствуют сеттеры. Такой объект 
      потокобезопасен (Thread-safe), его состояние нельзя случайно испортить в других 
      слоях программы.

3.  ОБОСНОВАНИЕ: Зачем ручное переопределение методов Object (без java.util.Objects)?
    - Глубокое понимание низкоуровневых механизмов: Использование Objects.equals() 
      скрывает под капотом автобоксинг и дополнительные вызовы методов. Ручная реализация 
      показывает чистоту владения базовым синтаксисом языка, исключает неявные 
      аллокации памяти и позволяет оптимизировать сравнение (например, в первую очередь 
      проверять ссылочную идентичность через 'this == o' и равенство примитивных ID).
    - Контроль контракта equals() / hashCode(): Студент обязан руками прописать 
      симметричность, рефлексивность и транзитивность алгоритма сравнения, что 
      гарантирует корректную работу объектов в хэш-коллекциях (HashMap, HashSet).

4.  ОБОСНОВАНИЕ: Разделение DAO на чтение и модификацию (CQRS Light)
    - Соблюдение принципа единственной ответственности (Single Responsibility Principle): 
      Класс, который занимается и сложными выборками, и обновлением данных, быстро 
      разрастается до тысяч строк. Разделение на FilmDaoImpl (поиск) и FilmUpdateDaoImpl 
      (сохранение/изменение) изолирует тяжелую логику SQL-маппинга от простых 
      операций записи. Это позволяет оптимизировать код: методы чтения могут работать 
      в режиме Read-Only (что ускоряет работу транзакций в СУБД), а методы записи 
      четко сфокусированы на операциях INSERT/UPDATE/DELETE.

5.  ОБОСНОВАНИЕ: Зачем нужен паттерн Specification?
    - Борьба с комбинаторным взрывом методов в DAO: В исходном коде под каждую задачу 
      приходилось писать отдельный метод: findRecentFilms(), getActorsByFilmName(), etc. 
      Если завтра бизнесу понадобится искать фильмы по стране, по первой букве имени, 
      или по комбинации "страна + год", нам пришлось бы дописывать новые и новые методы 
      в DAO, перекомпилируя весь слой данных.
    - Паттерн Спецификация превращает условия поиска в независимые объекты-строители SQL. 
      DAO содержит ОДИН метод query(Specification spec). Мы просто пишем классы 
      FindFilmsByYearSpecification или FindActorsByFilmSpecification, которые сами 
      знают, какой кусочек SQL-кода подставить и какие параметры забиндить в PreparedStatement. 
      Слой DAO становится закрытым для изменений, но открытым для расширения (Open/Closed Principle).

6.  ОБОСНОВАНИЕ: Зачем нужны Validator-классы перед Service?
    - Принцип «Fail-Fast» (Быстрый отказ): Система не должна тратить ресурсы на 
      открытие коннекта к БД и отправку SQL-запроса, если пользователь передал пустое 
      имя фильма или некорректную дату. Валидатор отсекает невалидный мусор на самой 
      ранней стадии, защищая базу данных от замусоривания, а приложение — от непредсказуемых 
      падений.

7.  ОБОСНОВАНИЕ: Почему запрещены System.out.println и SQLException на верхних слоях?
    - Управляемость логов: В реальном enterprise-приложении консоль сервера стирается 
      при перезагрузке, а вывод System.out.println несинхронен и тормозит поток выполнения. 
      Логгер (Log4J2) пишет данные в буферизированный файл асинхронно, разделяет логи 
      по датам (Rotated Logs) и позволяет менять уровень детализации (например, отключить 
      вывод отладочных логов на живом сервере одной строчкой в конфигурации xml, 
      без изменения кода программы).
    - Инкапсуляция исключений (Exception Wrapping): Слой бизнес-логики (Service) 
      не должен импортировать пакет java.sql.* и знать про SQLException. База данных 
      завтра может измениться с MySQL на PostgreSQL или на чтение из файлов. Если 
      мы пробросим SQLException в Service, нам придется переписывать весь проект. 
      Обертка в кастомные DaoException скрывает детали реализации базы данных и делает 
      архитектуру слабосвязанной (Loosely Coupled).

8.  ОБОСНОВАНИЕ: Почему в тестах запрещены ветвления (if, for, switch, циклы)?
    - Тесты не должны содержать собственную логику: Если в тесте появляется 'if' или 
      'for', это означает, что тест сам становится сложной программой. В коде теста 
      можно ошибиться так же, как и в основном коде. Если логика теста ошибочна, 
      он может показывать "зеленый свет" (успех) там, где программа на самом деле сломана.
    - Тест обязан быть максимально простым, линейным и легко читаемым:
      1) Подготовили данные (Arrange).
      2) Вызвали метод (Act).
      3) Проверили результат одной строчкой assert (Assert).
    - Вместо циклов JUnit 5 предоставляет мощный механизм @ParameterizedTest, который 
      выполняет итерации на уровне самого фреймворка, гарантируя изолированный прогон 
      каждого тест-кейса. Использование Mockito позволяет протестировать логику 
      сервиса мгновенно в оперативной памяти, не тратя секунды на реальное подключение 
      к MySQL, что делает сборку проекта быстрой и стабильной.
